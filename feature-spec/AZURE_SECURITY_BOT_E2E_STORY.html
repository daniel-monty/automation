Azure Security Bot — E2E API Automation Story (Planning Artifact)

Status: planning only — no test code included. This document defines the automatable end-to-end journeys for the Azure Security Bot feature as a story to be reviewed before any pytest implementation begins, following the conventions already established in this folder (api_calls.py, url_paths.py, users.py, conftest.py, test_api_calls.py).

Sources: PRODUCT-1519 (PRD extraction), MCPLAT-30866 (user stories), and direct verification of api/domains/bots/bots_azure/ + app/app/src/config/service/index.js. See AZURE_SECURITY_BOT_CONSOLIDATED_CONTEXT.md (session artifact) for full source detail.

1. Conventions this story follows

  • Base URL: tests run against --base_url (pytest option in conftest.py), same as existing canary tests — e.g. https://<stage>-api.montycloud.com/v1 becomes https://<stage>-api.montycloud.com + real Azure paths below (Azure bot paths are not under the legacy /v1 EC2-style prefix; they are their own API-Gateway custom-domain base path bots).

  • url_paths.py additions (new dict entries, one flow-call each, mirroring the existing flat "name": "/path" style):

    url_paths.update({
    "azure_bot_catalog": "/bots/azure/api/v1/bot-catalog",
    "azure_security_manifest": "/bots/azure/api/v1/security/manifest",
    "azure_security_subscriptions": "/bots/azure/api/v1/security/subscriptions",
    "azure_security_config": "/bots/azure/api/v1/security",              # POST/PUT/DELETE
    "azure_security_insights": "/bots/azure/api/v1/security/insights",
    "azure_security_findings": "/bots/azure/api/v1/security/findings",
    "azure_security_findings_suppress": "/bots/azure/api/v1/security/findings/suppress",
    "azure_security_findings_export": "/bots/azure/api/v1/security/findings/export",
})

    ⚠️ Use these real paths, not the PRD-documented /bots/azure / /bots/azure/security (missing /api/v1, and catalog is /bot-catalog not the bare domain root) — see gap #1/#2 below.

  • api_calls.py additions: one method per endpoint on api_call_wrapper, same shape as existing methods (self.base_url + url_paths[...], Authorization: token header, json.loads the response) — e.g. activate_azure_security_bot(self, sign_in_response, targets), deactivate_azure_security_bot(self, sign_in_response, scope, targets), suppress_azure_security_findings(self, sign_in_response, finding_ids, justification=None).

  • users.py: no new AWS-session logic needed for Azure flows (no boto3 Azure SDK calls in this domain's contract) — Azure flow methods can live directly on api_call_wrapper/ MontyCloudUsers using only requests, same as sign_in/list_regions.

  • test_input.yaml: add an azure_user_1 (or reuse user_1) block with azure_subscription_id, azure_subscription_name, azure_resource_groups: [] (empty = all RGs).

  • Fixtures: reuse user_object / sign_in_response from test_api_calls.py; add a retry-decorated poll helper (same pattern as check_instance_status) for scan-completion and offboarding-cleanup polling — both are async/event-driven, not synchronous API responses.

2. Flow 1 — Connect subscription → Activate bot → Trigger scan → Poll scan status

Setup: An Azure subscription must already be connected at the account/customer level (customeraccount domain — AZURE_PENDING_SUBSCRIPTIONS = /customeraccount/azure/api/v1/subscriptions/pending). This is out of scope for the bots domain and is a test-data precondition, not part of this story's API sequence — assume a pre-provisioned test tenant with ≥1 connected, healthy (ConnectionStatus != "connection_error") Azure subscription.

# Call Method + Path Expected status Assertions
1 Sign in POST /auth/signin 200 Data.Token present
2 List subscriptions GET /bots/azure/api/v1/security/subscriptions 200 response validates against SecurityBotSubscriptionsResponse (§7.4); Subscriptions non-empty; pick first with ConnectionError == false
3 Activate bot POST /bots/azure/api/v1/security body {"Targets":[{"SubscriptionId","SubscriptionName","ResourceGroups":["<rg-name-1>", ...]}]} — ResourceGroups must be non-empty 200 (409 if already active — treat as pre-existing state, not a failure, and continue); 400 if ResourceGroups is omitted/empty response validates against SecurityBotConfigResponse (§7.2); Status == "ACTIVE"; Targets echoes the subscription sent
4 (implicit) scan trigger none — POST .../security success publishes bots.azureSecurityBotActivated, consumed via EventBridge → SQS (azure-security-bot-scan queue) → ECS scan task, no direct HTTP trigger exists n/a —
5 Poll scan status GET /bots/azure/api/v1/bot-catalog (repeat with backoff, e.g. retry(wait_exponential_multiplier=2000, stop_max_attempt_number=15), mirroring check_instance_status) 200 response validates against AzureBotCatalogResponse (§7.1); poll until matching bot entry's Config.LastScanAt is non-null and Config.Status == "ACTIVE"

Teardown: none required here — bot stays active for Flow 2/3; final deactivation is Flow 4.

3. Flow 2 — Fetch findings → Suppress a finding

# Call Method + Path Expected status Assertions
1 Fetch findings GET /bots/azure/api/v1/security/findings?page=1&pageSize=25&sortBy=risk_level_numeric&sortOrder=asc&status=Failed 200 response validates against SecurityBotFindingsPageResponse (§7.6); Total >= 0; Findings is a list; each row has FindingId, IsSuppressed == false for at least one row (skip suppress step if Total == 0, log as inconclusive, don't fail the run)
2 Suppress finding PATCH /bots/azure/api/v1/security/findings/suppress body {"FindingIds": ["<FindingId>"]} 200 response validates against SuppressSecurityBotFindingsResponse (§7.7); SuppressedCount == 1; Message present
3 Re-fetch findings GET .../findings?...&resourceId=<same filter> 200 the suppressed FindingId now has IsSuppressed == true
4 Re-suppress (idempotency check) PATCH .../findings/suppress same FindingIds 200 SuppressedCount == 0 (already-suppressed findings are silently skipped per backend contract)

Gap flagged: the documented contract (POST .../findings/{findingId}/suppress with {"Justification": "..."}) does not exist. The only real endpoint is the bulk PATCH .../findings/suppress with {"FindingIds": [...]} (optional Justification). Automate against the bulk endpoint.

4. Flow 3 — Schedule a report

Reuses the generic report-schedule endpoint; Azure-specific inputs are platformReportType and Filters.

# Call Method + Path Expected status Assertions
1 Get filter options (subscriptions) GET /bots/azure/api/v1/security/insights/filter-options/subscriptions?Limit=20 200 response validates against SecurityBotFilterOptionsResponse (§7.5); Values non-empty (skip/inconclusive if empty, no scan data yet)
2 Get filter options (regions, resource-groups) GET .../insights/filter-options/{regions,resource-groups} 200 response validates against SecurityBotFilterOptionsResponse (§7.5); Values list present (may be empty)
3 Create schedule POST /reports/schedule body includes platformReportType: "AzureSecurityBotReport", Filters: {CheckIds, Severity, Subscriptions, ResourceGroups, Regions} 200/201 (pending — PRD-9 §5.8 flags this backend contract as unconfirmed; assert whatever the actual generic schedule endpoint returns for a new schedule, likely a ScheduleId) response contains a schedule identifier; ReportType/platformReportType echoes AzureSecurityBotReport

Setup: at least one recipient email in test data (test_input.yaml). Teardown: delete the created schedule via the existing generic delete_schedule_task-style endpoint (reuse url_paths['delete_schedule_task'] pattern) so repeated runs don't accumulate schedules.

Gap flagged: PRD-9 explicitly marks the backend schedule contract for Azure as an open question — confirm the real request/response shape against a live environment before implementing this flow; do not assume the shape above is final.

5. Flow 4 — Deactivate bot

# Call Method + Path Expected status Assertions
1 Deactivate (all) DELETE /bots/azure/api/v1/security body {"DeactivationScope": "all", "Targets": []} (body required even on DELETE) 200 response validates against DeactivateSecurityBotConfigResponse (§7.3); Status == "INACTIVE"; Message present
2 Confirm via catalog GET /bots/azure/api/v1/bot-catalog 200 response validates against AzureBotCatalogResponse (§7.1); matching bot's Config is null/absent or Config.Status == "NOT_CONFIGURED"/"INACTIVE"

Alternate case — selected deactivation (if the tenant has ≥2 subscriptions in scope): same call with {"DeactivationScope": "selected", "Targets": [{"SubscriptionId": "...", "ResourceGroups": []}]} (non-empty Targets required); assert the remaining scope in Config.Targets excludes the deactivated subscription and the bot stays ACTIVE if other subscriptions remain.

6. Flow 5 — Cleanup on account deletion (async, event-driven — not a direct API call)

Status: feature file to be added; implementation and execution skipped for now. Track this flow with a placeholder .feature/story file so it isn't lost, but do not implement or run it as part of the initial automation pass — see rationale below.

There is no synchronous "delete account" API endpoint in this domain. Cleanup is triggered by EventBridge events (customeraccount.azureOffboardingSuccess, customeraccount.azureDay2OnlyAccountDisconnectionCompleted) consumed by bots_azuresecuritybot_cleanup / process_azure_subscription_offboarded Lambdas, which hard-delete azure_security_bot_findings/bot_scope rows and deactivate any orphaned BotConfiguration.

Automating this flow requires either:

  • (a) a test harness that can publish the offboarding event directly to the relevant EventBridge bus (out of scope for pytest/requests-only API tests — would need boto3 events.put_events, similar to how users.py already uses boto3 sessions for AWS EC2 canaries), or
  • (b) driving the real account-offboarding flow through the customeraccount domain's own API (outside this story's scope) and then polling this domain's endpoints for the side effect.
# Call Method + Path Expected status Assertions
1 (setup, outside this domain) trigger account/subscription offboarding customeraccount domain API or direct boto3 events.put_events n/a —
2 Poll catalog GET /bots/azure/api/v1/bot-catalog (retry/backoff) 200 matching bot's Config becomes null/NOT_CONFIGURED within the retry window
3 (optional, needs DB access) direct query against azure_security_bot_findings/bot_scope tables — rows for the offboarded account_number are gone — not achievable via the public API; document as a DB-level assertion if the test harness has DB access, otherwise assert only via step 2

Recommendation: keep this flow as a lower-priority / separate test tier (e.g. a manual or boto3-assisted integration test rather than a pure requests-based canary), since it needs either event-bus publish rights or a real account-deletion trigger — flag this to the team before implementation. Per current direction: scaffold the feature file only; do not implement or execute this flow yet.

{
  "type": "object",
  "required": ["Targets"],
  "properties": {
    "Targets": {
      "type": "array",
      "minItems": 1,
      "items": {
        "type": "object",
        "required": ["SubscriptionId", "ResourceGroups"],
        "properties": {
          "SubscriptionId": { "type": "string" },
          "SubscriptionName": { "type": ["string", "null"] },

      }
    }
  }
}

ResourceGroups.minItems: 1 reflects the real model_validator behavior (§2 gap) — not the PRD's "empty means all" claim. Building a valid request today requires real RG names.
